# 智能体中心用户体验审查

审查日期：2026-09-16。对象：`web-admin` 工作目录当前版本，HEAD 为 `57f4aa8`，包含审查开始前已有的未提交调整。浏览器入口：`http://127.0.0.1:5185/#/agents`。

本次只审查并记录，没有修改应用代码、保存配置、发布版本、调整授权或删除演示数据。结论基于实际页面、截图观察、DOM 尺寸和当前源码；不以历史审查报告代替本次证据。

## 1. 总体判断

深绿侧栏、浅色工作区、白色表单面板的视觉语言基本统一，字体和控件也有共同基础。值得保留的是：三步创建、选填内容折叠、明确区分保存与发布、用户填写预览、交付效果示意，以及数字助理使用范围页的自然语言表达。

主要问题集中在信息优先级：页面较完整地陈列了配置字段，但没有持续把“现在能否使用、哪里需要处理、下一步做什么”放在最明显的位置。具体表现为异常使用绿色、同一对象切换两套导航、发布页缺少变更摘要、只读页仍陈列大量禁用表单，以及表格用较大空间展示低价值重复信息。

建议保留现有配色与组件基础，先重排状态、导航和信息，再统一字号、间距与密度。当前证据不足以支持推倒重做视觉系统。

优先级定义：P1 为可能导致状态误判或关键任务路径不清；P2 为明显增加阅读、比较和操作成本。以下属于专家审查判断，尚未进行真实用户可用性测试。

## 3. 优先问题

### UX-01 · P1 · 异常状态的文字、颜色和局部提示互相冲突

**观察事实**：专家团列表中，“会议全流程专家团”显示“依赖不可用”，标签却为绿色，与已发布标签相同。详情顶部出现红色提示“会议统筹专家：已归属其他专家团。新模拟任务已阻止”，但“队长与成员”页的队长选择框仍显示“会议统筹专家 · 可选”。

**影响**：扫视颜色会误认为团队健康；认真阅读后仍无法判断当前队长究竟是否可用。这里首先需要统一状态事实来源，单改颜色不能消除矛盾。

**建议**：

- 将“发布状态”和“可用状态”分别表达，例如“已发布 v1 / 当前不可用”。依赖不可用使用明确的异常色与图标，并给出原因和定位入口。
- 名称附近优先显示当前可用性；发布版本为次级信息。
- 列表、详情告警、队长选择项和成员卡使用同一次依赖判断，并正确传入当前团队身份。

**验收**：同一团队在所有页面的可用性一致；不可用状态不用成功色；点击异常能定位到具体依赖。当前现象已复现，实际归属冲突是否成立仍需独立检查业务校验，不能由本次视觉审查断言。

代码定位：[状态与标签](../../src/admin/campus/CampusCenter.tsx#L72)、[队长选择](../../src/admin/campus/TeamComposer.tsx#L7)、[状态颜色](../../src/admin/campus/campus.css#L1)。

### UX-02 · P1 · 同一专家切换两套信息架构，关键管理入口会离开首屏

**观察事实**：专家编辑采用“基本信息 / 工作能力 / 运行配置 / 检查配置”四步向导，同时在其上方放置“运行配置 / 发布管理 / 使用授权 / 版本与记录”。“运行配置”重复出现。进入“发布管理”后，页面改成左侧二级导航“概览 / 提示词 / 输入 / 输出 / 技能与工具 / 发布管理 / 使用授权 / 版本与记录”。进入编辑页时自动滚动到表单，管理入口会被滚出首屏。

**影响**：用户既要理解步骤，又要理解管理分区；同一配置在不同页面有不同名字和位置，保存后如何发布也不够直观。

**建议**：保留新建时的三步向导。已创建对象使用稳定的管理导航，例如“基本信息 / 工作能力 / 运行配置 / 发布与版本 / 使用授权 / 运行记录”；具体栏目可结合产品范围确认，但同一对象不能因切换页面更换整套导航。自动滚动只用于定位错误或明确跳转的字段，常规进入页面应保留对象、状态和管理导航。

**验收**：编辑、授权、发布之间切换时导航位置和名称不变；只有一个“运行配置”入口；常规进入页面能看见当前对象、状态和下一步入口。

代码定位：[两套页面路由分流](../../src/admin/campus/CampusCenter.tsx#L65)、[编辑页额外入口](../../src/admin/campus/ExpertForm.tsx#L129)、[自动滚动](../../src/admin/campus/ExpertForm.tsx#L73)。

### UX-03 · P1 · 发布页强调“可以发布”，却没有提供足够的核对信息

**观察事实**：数字助理发布页主要展示当前版本、一条绿色检查通过提示和“确认生效”。确认弹窗列出版本、名称和开场白，并要求填写“这次改了什么”，没有展示与当前生效版本的差异。专家发布页同样主要是“检查通过 + 模拟发布”。数字助理首页已有“有待发布的草稿”，但唯一实色主按钮仍是“编辑配置”。

**影响**：用户需要记住刚才改过的内容，再自行描述，无法在发布动作前复核；状态变化没有带动主操作变化。

**建议**：发布页先展示“本次变更”，再展示“生效影响”和“检查结果”。优先列出模型、提示词、工作能力、输入输出等实际发生变化的项目；未变化的内容折叠。清楚区分当前生效版与待发布草稿。首页按状态给主操作：有待生效修改时突出“核对并生效”，检查失败时突出“完善配置”。

**验收**：不离开发布页即可知道改了什么、影响谁、何时生效以及是否存在阻塞项；检查通过不应暗示真实执行效果已验证。

代码定位：[数字助理主按钮](../../src/admin/campus/AssistantSettings.tsx#L23)、[发布页](../../src/admin/campus/CampusCenter.tsx#L181)、[发布弹窗](../../src/admin/campus/CampusCenter.tsx#L196)。

### UX-04 · P1 · 专家团只读页的信息顺序与查看任务不匹配

**观察事实**：“队长与成员”页先显示队长编辑控件，再展示全部 10 位普通专家候选卡，其中多位未发布或已停用。当前已选的 2 位成员及其固定版本排在候选集合之后。只读状态下仍保留全部候选项、禁用的添加/移除控件，并继续展开队长的大段输入输出配置。

**影响**：查看团队组成需要从不可操作的配置项中找答案，页面长度明显超过任务所需。当前异常与成员关系也难以形成整体认识。

**建议**：只读页首屏展示“队长 + 已选成员 + 固定版本 + 可用性 + 更新提示”的紧凑关系摘要。输入输出展示已配置结果，细节按需展开。进入编辑后再通过“添加成员”打开候选选择；可用成员优先，不可用成员单独折叠并说明原因。

**验收**：打开已有团队即可识别队长、已选成员、引用版本和异常对象；不需要滚过完整候选库。只读内容使用文本/摘要，禁用输入框仅在保留结构确有必要时使用。

代码定位：[候选与已选成员的顺序](../../src/admin/campus/TeamComposer.tsx#L21)、[队长输入输出嵌入](../../src/admin/campus/CampusCenter.tsx#L175)。

## 5. 实测视觉问题

### 5.1 列表留白很多，但有效信息容量低

在当前 11 条智能体数据下：

| 指标 | 1440×1000 | 1280×800 |
| --- | --- | --- |
| 表格表头距视口顶部 | 约 425px | 约 425px |
| 首条数据距视口顶部 | 约 467px | 约 467px |
| 首条数据行高 | 126.5px | 165px |
| 首屏完整数据行 | 4 行 | 2 行 |

1280px 宽度时，“查看 / 编辑 / 管理 / 删除”四个操作竖排，模型名称也换行，进一步撑高行。页面本身未出现横向溢出，但“没有溢出”并不等于浏览效率合格。

调整方向：压缩演示身份条和重复的页面说明；减少低价值重复字段；用两行以内的对象信息配合一行能力摘要，常用操作集中。以同样 1280×800 尺寸下首屏至少完整显示 4 条为第一轮设计目标，同时保持正文易读。该数值是本次建议验收目标，并非已经实现。

### 5.2 字号偏小、灰绿层级过多

DOM 实测：列表表头 11px，名称 14px，责任人、使用方式、版本和能力数量多为 12px。责任人与版本等文字色为 `rgb(139,150,126)`，名称为 `rgb(54,69,42)`，大面积背景又是接近的浅绿/浅灰。重要状态与辅助说明容易混在一起。

建议第一轮统一为：页面标题 24–28px、区块标题 16–18px、主要内容 14px、辅助内容 12–13px。重要状态及使用范围不能只靠小号浅灰字表达；绿色用于正常/成功，异常和待处理使用不同语义，并配文字或图标。上述为项目内设计建议；本次没有做完整可访问性合规判定。

### 5.3 面板和标题重复，增加纵向阅读距离

多个区域出现“折叠标题 → 同名区块标题 → 说明 → 字段标题”，如“人工兜底”“输出与验收”“模型与上下文”。一个默认模型下拉框也占据整块较高面板。应减少重复标题与不必要的面板内边距，将空间给内容预览、状态和错误定位。

### 5.4 当前范围与页面文案有残留冲突

当前 PRD 声明后台暂不调试，发布不依赖后台测试报告，但队长能力页仍出现“版本更新后重新测试”，组团说明仍写“随本专家团测试和发布”。这些文字会暗示不存在的下一步。应按当前范围统一为检查配置/发布，或明确说明测试发生在何处；不应只保留一个含混指令。

## 6. 建议实施顺序与验收

1. **先统一状态事实与语义**：修复依赖状态冲突、异常标签颜色、授权保存语义。验收应同时检查列表、详情与局部控件。
2. **统一已有对象的导航**：建立一套稳定管理分区；新建保持向导。验证从编辑到发布、授权再返回时，当前对象、分区和草稿状态始终明确。
3. **补齐关键决策信息**：发布页展示变更与影响；团队页优先展示已选组成；任务详情优先展示结果与待处理项。
4. **统一视觉密度与字级**：调整列表列宽、行内操作、顶部占高、折叠摘要和只读呈现；在 1440×1000 与 1280×800 两种尺寸重验。
5. **校正文案与页面一致性**：创建步骤样式、按钮主次、术语、空状态、禁用原因以及已取消测试流程的遗留提示。

验收应围绕代表性任务：找到一个不可用团队并识别原因；核对草稿改动并判断能否发布；查看谁能独立使用专家；识别团队固定成员及版本；配置用户输入并确认预览；从运行记录判断任务实际结果与下一步处理人。不要仅以页面能打开、按钮可点击或构建成功作为体验验收。
