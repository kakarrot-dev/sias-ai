# 前后台原型功能闭环审查

审查日期：2026-09-17。对象：`sias-ai` 当前工作区的高校单专家原型。

**结论：局部流程成立，前后台整体尚未闭环。** 当前能演示管理员配置专家，以及师生找专家、创建个人专家、聊天和管理历史；还不足以完整说明“平台提供服务 → 用户具备使用条件 → 完成任务 → 获得成果 → 遇到异常后恢复”的全过程。

这不是因为没有真实接口。独立演示数据符合原型阶段边界；主要问题是两端对同一对象、状态和用户动作的约定尚未完整对应。即使未来接通服务，下列产品决策仍需要先明确。

本地未找到独立命名为 `pm-skill` 的技能文件。本次实际采用已安装的 PM 技能：[用户旅程](/Users/kakarrot/.codex/skills/customer-journey-map/SKILL.md)、[验收场景](/Users/kakarrot/.codex/skills/test-scenarios/SKILL.md)、[风险预演](/Users/kakarrot/.codex/skills/pre-mortem/SKILL.md)。以学生学习、教师材料处理、用户自建专家、管理员运营四类任务为审查入口；用户心理与影响属于产品判断，没有冒充访谈结论。

审查内容为页面、入口、展示字段、操作结果、状态说明、异常恢复和前后台职责。没有审查后端代码、API 实现、数据库、Runtime、安全实现或模型实际效果，也没有把历史自动化测试数量当作本轮证据。

## 2. 从用户旅程看覆盖情况

“局部成立”表示原型可表达该段操作，不表示已连接真实服务。“存在断点”表示缺少跨页面的产品规则或状态样例。

| 使用阶段与角色 | 用户想完成什么 | 前台表现 | 后台支撑 | 判断 |
| --- | --- | --- | --- | --- |
| 学生首次使用 | 直接向助理提问 | 默认助理、快捷问题、输入区、演示说明 | 普通专家配置可见，默认助理当前没有管理入口 | 存在断点：默认服务归属不清 |
| 师生找专家 | 找到适合自己的服务并理解用途 | 32 位、10 类，学生/教职工筛选，详情到独立聊天 | 发布、草稿、停用齐备；当前表单未对应人群与用途分类 | 局部成立，市场供给未闭环 |
| 学生学习问答 | 发送问题并继续交流 | 自建样例发送后身份正确，回复明确标为演示 | 模型、提示词、开场白、推荐问题可配置 | 正常文字交互局部成立 |
| 教师处理文献 | 提供材料并获得可用的阅读结果 | 文献阅读入口、附件入口、富文本示例 | 输入输出格式、能力配置存在 | 缺处理失败与成果交付样例 |
| 用户调用外部能力 | 查看文档、发送通知或修改材料 | 创建页承诺本人授权范围、执行前本人确认 | 能力与具体操作、版本、身份、确认规则 | 缺授权—确认—执行—结果闭环 |
| 用户自建专家 | 创建仅供自己使用的助手 | 四分区创建、预览、创建即聊天、“我创建的” | 后台主要描述管理员发布后所有正常用户可用 | 私有对象与公共对象边界未对齐 |
| 用户查看消耗 | 知道用了多少、还能否继续 | Token、积分余额、消耗积分 | Token、USD 费用、钱包/Key/订阅额度 | 计量与扣费解释未闭环 |
| 用户遇到不可用 | 理解原因并恢复使用 | 当前主流程以可聊天状态为主 | 账号、专家、模型、Key 有多种不可用状态 | 后台状态缺前台承接 |
| 用户回访 | 找回历史继续聊天 | 归档—恢复实测保留样例身份和消息 | 历史版本、会话及模型调用追溯 | 历史管理局部成立，停用后续聊规则待补 |
| 管理员支持用户 | 定位失败并说明下一步 | 未观察到问题反馈或诊断编号入口 | 会话、模型失败、费用及审计详情 | 模型诊断较完整，服务处理未闭环 |

用户首次获得价值的时刻，是看到与当前问题相关且能继续使用的答复或成果。当前原型对“找到专家并开始聊天”的表达较清楚，对“为什么不能用”和“这次任务究竟完成了没有”的表达不足。

## 3. 已具备的产品基础

1. **后台配置主干清楚。** 六个模块职责基本稳定；专家采用基础与提示词、模型配置、执行能力、输入输出四分区。草稿和已发布版本有区分，发布记录说明保留快照。
2. **能力配置有边界。** 能力导入弹窗提供格式、数量、体积及重复项规则；写操作在配置中声明执行前确认。没有把“上传定义”描述成“真实执行已成功”。
3. **用户与调用统计较克制。** OIDC 身份、平台账号和模型使用条件分开；模型调用缺报不当作零消费；平台 Key 与个人 Key、本平台调用与上游统计、费用与实际费用分别展示。
4. **前台基础路径可理解。** 当前仓库已实测教职工筛选及文献搜索、详情进入对应专家会话、自建专家进入聊天、首次发送显示正确身份、归档与恢复保留消息。
5. **现有富文本与表单值得复用。** “Agent 产品讨论”已展示表格、JSON、检查清单和“补充文档需求”表单。该表单用于收集需求，不能等同于外部操作的执行授权或成果验收。

这些基础不需要整体推翻。下一轮应优先补跨端规则和少量代表性状态页。

## 4. 按影响排序的问题

P1：若要宣称当前单专家场景已经前后台闭环，应先补齐。P2：改善持续使用与运营体验，不阻塞基础聊天演示。本次识别 7 项 P1、2 项 P2；均为原型产品问题，不是代码漏洞结论。

### R1 · P1：前台服务目录与后台供给对象没有完整对应

**证据：** 前台有默认助理、学生与教职工两类浏览范围、10 个用途分类及 32 位内置专家。后台当前实例显示 7 位普通专家，创建页只有名称、简介、模型、提示词、开场白及推荐问题等；未提供当前市场所需的人群与用途分类。最新后台范围明确不开放数字助理配置。[前台契约](/Users/kakarrot/Dev/sias-ai/frontend/prototypes/macos-client-v2/SINGLE_AGENT_V01.md)与[后台当前范围](/Users/kakarrot/Dev/sias-ai/admin/docs/audits/2026-09-17-expert-capability-mvp.md)可以交叉核对。

**影响：** 管理员创建“文献阅读助手”后，无法从当前页面约定判断它如何进入“教职工常用 → 科研支持”，也无法明确默认助理由谁维护。两端示例数量不同本身不构成缺陷；缺少对象和展示字段的映射才是问题。

**最小补充：** 定义“默认助理、平台公共专家、个人专家”三个来源及其维护方；为平台专家补充人群标签和用途分类，或明确固定分类的维护规则。人群标签用于发现，不自动变成权限。默认助理可以是系统固定服务，只需明确配置与可用性归属，不必恢复旧总管功能。

**验收：** 用同一位专家演示后台配置、发布、前台分类检索、详情、对话和运行追溯；静态数据也要让名称、标识、版本和模型约定对应。

### R2 · P1：个人创建与平台发布是两种产品对象，当前规则没有明确分开

**证据：** 当前前台实测“原型审查样例”创建成功后直接进入聊天，无发布动作；目录提供“我创建的”。后台页面主要说明“管理员创建和发布专家，所有正常登录用户可用”，没有当前个人专家的归属及适用规则说明。前台契约明确已有个人专家暂不提供编辑、删除、发布入口。

**影响：** 无法仅凭原型回答：个人专家是否只对本人可见、能否进入公共目录、后台是否可见其配置、账号停用后如何处理、使用哪些能力和额度。不能把公共专家“发布后所有人可用”的规则直接套到个人对象。

**最小补充：** 建议首期明示“个人专家仅本人可用、不进入公共发布流程”，并说明其调用仍受账号、模型、能力和额度状态约束；后台只需要约定必要的归属、状态与使用统计，不默认暴露私有提示词或聊天正文。发布到公共市场属于另一个后续决策。

**验收：** 个人专家与平台专家分别标明来源、所有者和可见性；用两个演示用户说明个人对象不会出现在另一用户的目录。编辑、删除是已明确排除的本期能力，不作为强制补项。

### R3 · P1：后台要求用户主动连接 Key，前台没有完成该动作的路径

**证据：** 后台用户中心“周宁 → 模型接入”显示“待用户连接”，要求用户前往 Token超市选取或创建专属 Key，再主动连接；来源切换明确只是查看。前台个人中心只有基本资料与归档会话，没有对应的来源选择、连接状态、主动连接或重新连接入口。[双 Key 设计](/Users/kakarrot/Dev/sias-ai/admin/docs/audits/2026-09-17-oidc-user-run-design.md)还规定异常时不自动切换来源。

**影响：** 后台能知道用户被什么阻断，用户却没有可执行的恢复动作；管理员也不能代用户连接，因此形成操作死路。登录成功不等于能开始聊天。

**最小补充：** 用前台个人中心或聊天阻断卡表达当前调用来源、费用承担、可用状态及相应下一步；补首次连接、过期重新连接、额度不足、无目标模型四类样例，并保留原会话和输入。登录页、登录失效和账号停用也应有可演示入口。原型使用脱敏假数据，不要求接入真实凭证。

**验收：** 从“待连接/过期”进入处理页，取消仍回原会话；完成演示连接后返回原输入。无授权不得静默切换到平台额度。

### R4 · P1：能力配置已恢复，用户确认、执行结果与运行追溯仍停留在聊天层

**证据：** 前后台创建页都提供 Skill、Tool、MCP，包含通知下发、校内日程和文档修改，前台写明“修改或发送前由本人确认”。运行中心只有会话记录、模型调用、用量统计、管理审计；[最新后台说明](/Users/kakarrot/Dev/sias-ai/admin/docs/web-admin-spec.md)明确移除了人工确认、执行结果及继续办理展示。当前前台文档需求表单仅保留信息，不是发送通知的确认卡。

**影响：** 对“发出通知”这样的单专家任务，用户仍不知道将发送给谁、发送什么、取消是否生效、超时后是否已经发送；管理员只能看到模型状态，无法解释外部动作结果。回复成功不能证明通知成功。

**最小补充：** 保持单会话产品，不恢复专家团或业务中心。在对话中补“待授权/待确认 → 执行中 → 成功/失败/结果待核实”的代表样例；确认展示对象、内容和范围，拒绝有明确结果。运行详情增加同一次操作的能力名称、确认结果、执行状态、结果引用和恢复责任。

**验收：** 通知发送至少演示确认成功、用户拒绝、授权不足、超时结果未知四条路径；结果未知先核实原动作，不把重发整段聊天作为默认恢复。

### R5 · P1：输入输出配置尚未形成用户可理解的材料处理与成果领取流程

**证据：** 后台输入输出仅配置格式，支持文档、表格、图片、音频及 Word/PDF/JSON/CSV 等输出。前台“文献阅读助手”详情只有用途介绍和开始对话，未说明该专家需要什么文件、限制是什么、会得到什么形式的成果。当前已有附件展示、富文本、JSON 示例和需求表单，但未观察到与专家输出配置对应的成果生成、领取失败及恢复样例。[输入输出范围](/Users/kakarrot/Dev/sias-ai/admin/docs/audits/2026-09-17-expert-capability-mvp.md)明确它们目前只是格式约定。

**影响：** 教师无法在提交前判断材料是否合适，也无法区分“选择了本地文件”“已读取材料”“已经生成 Word”。格式选项本身不足以承诺一次任务完成。

**最小补充：** 在详情或输入区显示支持格式和必要限制，可采用全局规则，不必恢复复杂配置表单；补材料待处理/不支持/读取失败/可重选状态。成果采用统一卡片表达名称、格式、生成状态、预览或下载及失败重试；多格式如何选择也需一句明确规则。

**验收：** 用“提交文献 → 生成阅读摘要和一个文件成果”走通成功、材料失败、成果生成失败三条原型路径。示例下载明确标记为样例文件。

**验证边界：** 本轮没有上传文件验证格式拦截，不能据此断言现有选择器接受了不支持的文件；此处结论针对可见规则和场景表达不完整。

### R6 · P1：前台积分与后台费用、额度之间没有统一的产品解释

**证据：** 前台个人中心展示 1,000 积分余额、每条消耗积分和 Token；后台展示 USD 费用、实际费用、钱包、Key、订阅额度，没有积分对应说明。前台契约明确积分余额是独立样例，不通过金额或 Token 换算；后台也明确费用不等于钱包扣款。

**影响：** 用户无法理解“积分还有，为什么 Key 额度不足”“用个人 Key 是否还扣积分”“失败或停止为什么有消耗”；管理员不能依据现有页面解释同一笔记录。样例总数不同不是计算错误，缺少语义关系才是问题。

**最小补充：** 先明确积分到底代表平台使用额度、奖励权益还是独立展示，以及个人 Key 模式是否适用；若尚未决策，应在原型中明确未适用范围，避免展示成已确定扣费规则。采用同一演示用户、同一次调用对齐前台用量与后台记录，不强行把三类额度相加或自行推导换算率。

**验收：** 成功、失败但有已上报消耗、用量待补报、额度不足各有一条前后台对应示例；用户能理解本次消耗和能否继续使用。

### R7 · P1：后台启停和依赖变化，缺少前台新会话与历史续聊的状态约定

**证据：** 后台有已停用专家、账号启停、模型及中转站启停；发布记录说明已有会话按原版本追溯。前台契约以“所有目录智能体均可进入演示会话”和历史身份保留为主，未完整定义已停用、模型下线、Key 无权使用目标模型时的卡片、发送动作及归档恢复结果。[模型状态规则](/Users/kakarrot/Dev/sias-ai/admin/docs/audits/2026-09-17-relay-model-catalog.md)已定义后台不可选择及发布约束。

**影响：** “历史还能看”与“能否继续发送”容易混为一谈；管理员停用后用户该看到什么、已打开的输入怎么办、恢复后用哪个版本，都无法从当前原型得到一致答案。

**最小补充：** 定义状态到用户动作的映射：能否发现、能否新建、能否续聊、是否保留草稿和历史、谁可以恢复。建议历史可读与新调用资格分开；新发布采用新版本，历史快照保留，历史续聊的采用规则需明确，不能仅写“可追溯”。

**验收：** 同一示例专家演示发布新版本、停用、重新启用和模型不可用；从目录、新会话、已打开会话、归档恢复四个入口查看同一套规则。

### R8 · P2：问题从用户到后台再回到用户的处理链较弱

**证据：** 前台消息有复制和本地演示标识，未观察到问题反馈及可供报障的编号入口；后台失败详情有调用编号、HTTP 504 和处理建议，但没有与用户反馈的关联示例。后台不展示聊天正文是当前明确边界，应保留。

**影响：** 用户描述“刚才那个专家失败了”时，管理员难以准确定位；模型成功但内容不合用，也不会体现在仅有调用状态的统计中。

**最小补充：** 优先给失败提示提供可复制的诊断编号和求助指引；后续可增加轻量的问题类型、处理状态和结果通知。不要求本期建设完整工单系统，也不建议默认采集或开放全部聊天正文。

**验收：** 一条失败反馈可以对应到正确用户、会话和调用；涉及内容时用户明确选择提供哪些材料；管理员给出的下一步能回到用户当前任务。

### R9 · P2：已覆盖教职工场景，个人身份展示仍只采用学生标签

**证据：** 前台市场明确提供“教职工常用”及 12 位相关专家，个人中心却固定展示“学号”；后台主要展示 OIDC 来源和展示名，没有前台学号/工号展示规则的对应说明。

**影响：** 教职工可能误以为使用了错误身份；身份缺少校园编号时也缺少合适的文案。演示姓名不同不是身份串联缺陷的证据。

**最小补充：** 将资料标识设计为学号/工号或“校园身份编号”，注明外部来源只读，缺失时显示未提供；是否区分师生只用于展示及默认推荐，不追加角色授权系统。

**验收：** 学生、教职工、无校园编号三种资料样例均能显示合理标签，并可关联同一本地用户及其用量。

## 6. 不应误判为本期问题的事项与待决策项

以下属于已知原型边界，不列为缺陷：未连接真实模型/OIDC/工具、页面内存刷新重置、后台浏览器保存、固定演示统计、没有专家团和会议事项、知识库未开放、没有复杂角色授权、没有后台聊天正文、个人专家暂不开放编辑和删除。

本次也不要求恢复历史版的后台调试、完整输入表单设计器、多人交付治理或业务中心。对执行型专家，只需在当前对话与运行详情补最小状态表达即可。

仍需产品确认的前提是：个人专家是否固定私有；积分的业务含义及个人 Key 是否适用；默认助理是系统固定服务还是普通可配置对象；新版本发布后历史续聊采用哪个版本。这些不能从当前页面推导为既定事实。

真实回答是否准确、文献引用是否可靠、陪伴场景的实际质量、真实授权是否有效，均不在本次原型审查的证据范围内。不能因一次演示成功给出这些方面的结论。
